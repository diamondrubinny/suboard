# SUBoard — מערכת ניהול עבודה ליחידת הבטיחות

> מסמך אפיון ותוכנית עבודה. מקור אמת אחד לתכנון — כל שלב נבנה לפי המסמך הזה.
> סטטוס: **שלבים 1–2, גלים A–E ו-SSO/SCIM נבנו ונבדקו** — 127 בדיקות אוטומטיות (18 משותפות + 109 שרת), 8 סדרות e2e בדפדפן על build פרודקשן, axe: 0 הפרות ב-99 מסכים/מצבים · המשך לפי `docs/FEATURES_ROADMAP.md`.

## 1. סיכום ההבנה

המשתמש ביקש "מערכת כזאת" על בסיס קובץ `scripts-full.zip`.
**ממצא:** הקובץ הוא לכידת דפדפן של **דף הבית השיווקי של monday.com** — 90 קבצי JS:
סקריפטי מעקב ופרסום (GTM, Meta Pixel, Hotjar, Bing, LinkedIn, Reddit, X, HubSpot, Capterra וכו'),
אנימציות Webflow/GSAP, ו-bundles של ספריות (React, MobX, date-fns). **אין בו לוגיקת מוצר**, ואין
בו דבר שמותר או כדאי להעתיק. לכן נבנתה מערכת **מקורית** בקונספט דומה — *לוחות עבודה גמישים
(Boards)* — מותאמת לתהליכי יחידת בטיחות, בעברית ו-RTL, ובלי שום tracker צד שלישי.

### ערך עסקי
- ריכוז כל תהליכי היחידה (אירועים, סקרים, פעולות מתקנות, הדרכות, בדיקות ציוד, היתרי עבודה) במקום אחד.
- מעקב אחר תאריכי יעד ופריטים באיחור — מניעת "נפילות בין הכיסאות".
- תיעוד ושקיפות: היסטוריית פעולות ועדכונים לכל פריט (חשוב לביקורות ולתחקירים).
- מערכת פנימית, מבוקרת הרשאות, ללא דליפת מידע לצדדים שלישיים.

### הנחות עבודה (ניתן לשנות)
| # | הנחה |
|---|------|
| 1 | ארגון אחד (יחידת בטיחות אחת); 5–50 משתמשים; עד עשרות אלפי פריטים. |
| 2 | מערכת פנימית — אין הרשמה ציבורית; מנהל מערכת יוצר משתמשים. |
| 3 | פריסה on-prem / VM ארגוני מאחורי HTTPS (reverse proxy). |
| 4 | עברית בלבד בשלב 1 (מבנה הקוד מאפשר i18n בהמשך). |
| 5 | העלאת קבצים — **לא** בשלב 1 (דורשת הסגר וסריקת נוזקות — שלב 2). |
| 6 | SQLite בשלב 1; מעבר ל-PostgreSQL מתוכנן כאשר יש צורך ב-HA/עומס. |

### שאלות פתוחות (לא חוסמות)
1. האם נדרשת התחברות SSO ארגונית (Azure AD / Entra ID, SAML)? — משפיע על שלב 2.
2. האם המערכת תכיל מידע רפואי על נפגעים? (ההמלצה: **לא** — רק הפניה למערכת ייעודית.)
3. היכן תותקן (שרת ארגוני / ענן)? מדינת אחסון?
4. האם נדרשות התראות דוא"ל (יעד מתקרב/עבר)? דרך איזה שרת SMTP?
5. האם צריך ייצוא לאקסל / PDF לדוחות הנהלה?

## 2. MVP — היקף שלב 1

**בפנים:**
- התחברות אימייל+סיסמה, Session מאובטח, נעילה אחרי ניסיונות כושלים, החלפת סיסמה.
- ניהול משתמשים ותפקידים (מנהל מערכת).
- לוחות (Boards) עם קבוצות (Groups), עמודות (Columns) ופריטים (Items).
- סוגי עמודות: טקסט, טקסט ארוך, מספר, סטטוס (תוויות צבעוניות), אנשים, תאריך, תיבת סימון.
- 9 תבניות מוכנות ליחידת בטיחות (ראו §6; גל E הוסיף מלאי חומ"ס ומפגעים).
- תצוגת טבלה (מקובצת) + תצוגת קנבן לפי עמודת סטטוס, חיפוש וסינון.
- חלון פריט: שדות, עדכונים/הערות, היסטוריית פעולות.
- לוח בקרה אישי: הפריטים שלי, באיחור, תמונת מצב לכל לוח.
- הרשאות ברמת לוח (בעלים / עורך / צופה).
- יומן ביקורת (Audit) לאירועי אבטחה.
- עמודי הצהרת נגישות, פרטיות, עוגיות, תנאי שימוש (טיוטות), סרגל נגישות.

**מחוץ לשלב 1:** קבצים מצורפים, התראות דוא"ל, SSO/MFA, ייצוא, תצוגת לוח שנה, טפסי דיווח
ציבוריים, אוטומציות ("כאשר סטטוס = X → ..."), אפליקציית מובייל נייטיב (ה-Web רספונסיבי).

## 5. ארכיטקטורה

```
Browser (React SPA, RTL)
   │  HTTPS, cookie session (HttpOnly, Secure, SameSite=Strict)
   ▼
Reverse proxy (nginx / IIS / Caddy) — TLS, HSTS
   ▼
Node.js — Fastify API (TypeScript)
   ├─ plugins: helmet (CSP), rate-limit, cookie, CSRF guard, auth
   ├─ routes  → services (business logic + authorization) → repositories (SQL)
   └─ serves built SPA (static)
   ▼
SQLite (WAL) — קובץ יחיד, גיבוי פשוט  →  (שלב 3: PostgreSQL)
```

### החלטות טכנולוגיות וחלופות
| רכיב | בחירה | למה | חלופות | מגבלות |
|------|-------|-----|--------|--------|
| שפה | TypeScript | טיפוסים משותפים לקליינט/שרת | JS | שלב build |
| API | Fastify 5 | מהיר, plugins רשמיים לאבטחה, `inject` לבדיקות | Express, NestJS | אקוסיסטם קטן מ-Express |
| DB | SQLite (better-sqlite3) | אפס תשתית, טרנזקציות, גיבוי = קובץ | PostgreSQL | כותב יחיד; לא ל-HA |
| ולידציה | Zod (חבילה משותפת) | אותה סכמה בקליינט ובשרת | Valibot, Yup | — |

## 7. סכמת בסיס נתונים

```sql
users(id PK, email UNIQUE, name, password_hash, role[admin|manager|member], is_active,
      must_change_password, failed_logins, locked_until, last_login_at, created_at, updated_at)
sessions(id PK = sha256(token), user_id FK, created_at, expires_at, last_seen_at, user_agent)
boards(id PK, name, description, template_key, created_by FK, created_at, updated_at, archived_at)
board_members(board_id FK, user_id FK, role[owner|editor|viewer], PK(board_id,user_id))
groups(id PK, board_id FK, name, color, position)
columns(id PK, board_id FK, title, type, settings JSON, position)
items(id PK, board_id FK, group_id FK, name, "values" JSON, position, created_by, created_at, updated_at)
updates(id PK, item_id FK, user_id FK, body, created_at)
activity(id PK, board_id FK, item_id, user_id, action, detail JSON, created_at)
audit_log(id PK, user_id, event, ip_hash, meta JSON, created_at)
```
- ערכי עמודות נשמרים ב-`items.values` כ-JSON לפי מזהה עמודה, ועוברים ולידציה בשרת לפי סוג העמודה.
- `ON DELETE CASCADE` מלוח → קבוצות/עמודות/פריטים/עדכונים.
- כתובת IP נשמרת ביומן הביקורת רק כ-HMAC (לא בטקסט גלוי) — מזעור מידע.

## 8. API

כל הנתיבים תחת `/api`. כל נתיב פרט ל-`/auth/login` ו-`/health` דורש Session.
כל בקשה משנה מצב (POST/PATCH/PUT/DELETE) דורשת כותרת `X-Requested-With: suboard` ו-Origin תואם.

| Method | Path | הרשאה |
|--------|------|-------|
| GET | `/health` | ציבורי |
| POST | `/auth/login` | ציבורי (rate-limited) |
| POST | `/auth/logout` · GET `/auth/me` · POST `/auth/change-password` | מחובר |
| GET | `/users/directory` | מחובר (id+שם בלבד, לבחירת אחראי) |
| GET/POST | `/users` · PATCH `/users/:id` | admin |
| GET | `/templates` | מחובר |
| GET/POST | `/boards` | מחובר / admin+manager |
| GET/PATCH/DELETE | `/boards/:id` | צופה / בעלים / בעלים |
| PUT/DELETE | `/boards/:id/members[/:userId]` | בעלים |
| POST | `/boards/:id/groups` · PATCH/DELETE `/groups/:id` | עורך |
| POST | `/boards/:id/columns` · PATCH/DELETE `/columns/:id` | בעלים |
| POST | `/boards/:id/items` · PATCH/DELETE `/items/:id` | עורך |
| GET/POST | `/items/:id/updates` · DELETE `/updates/:id` | צופה / עורך / כותב או בעלים |
| GET | `/boards/:id/activity` · `/items/:id/activity` | צופה |
| GET | `/dashboard` | מחובר (רק לוחות שהוא חבר בהם) |
| GET | `/admin/audit` | admin |

**הגנת IDOR/BOLA:** כל נתיב שמקבל מזהה משאב (פריט/עמודה/קבוצה/עדכון) מאתר את ה-`board_id`
של המשאב בשרת ובודק חברות והרשאה *לפני* כל פעולה. מזהים הם UUID אקראיים.

## 9. אבטחה — Threat Model (תקציר; פירוט ב-`docs/SECURITY.md`)

| נכס | איום | סיכון | בקרה |
|-----|------|-------|------|
| חשבונות | Brute force / credential stuffing | גבוה | rate-limit ל-IP, נעילת חשבון, הודעת שגיאה גנרית, scrypt |
| Session | גניבת cookie / CSRF | גבוה | HttpOnly+Secure+SameSite=Strict, token אקראי 256bit נשמר כ-hash, כותרת מותאמת+בדיקת Origin, תפוגה מוחלטת+חוסר פעילות |
| נתוני לוחות | IDOR בין לוחות | גבוה | בדיקת הרשאה בשרת לכל משאב, בדיקות אוטומטיות |
| נתונים | XSS | בינוני | React escaping, ללא `dangerouslySetInnerHTML`, CSP קשיח, צבעים מרשימה סגורה |
| נתונים | SQL Injection | בינוני | שאילתות פרמטריות בלבד |
| זמינות | הצפה | בינוני | rate-limit גלובלי, הגבלת payload (100KB) |
| פרטיות | מידע רגיש בטקסט חופשי | בינוני | הנחיה בממשק, מדיניות שמירה, הרשאות לוח |

## 10. פרטיות, עוגיות ונגישות

- **Data Map** מלא ב-`docs/PRIVACY.md`.
- **עוגיות:** עוגייה חיונית אחת בלבד (`sb_session`). אין אנליטיקה, אין פיקסלים, אין CDN חיצוני

  (בחירת סטטוס), סרגל נגישות (הגדלת טקסט, ניגודיות גבוהה, הדגשת קישורים, עצירת אנימציות).

## 12. סיכונים ונושאים לבדיקה מקצועית

- **רגולציה:** דיווח אירועי בטיחות עשוי להיות כפוף לדרישות פקודת הבטיחות בעבודה ותקנות ארגון הפיקוח —

- **פרטיות:** מידע על נפגעים (שם, פגיעה) עלול להיות מידע רגיש לפי חוק הגנת הפרטיות (כולל תיקון 13) —
  *דורש בדיקה משפטית / ממונה פרטיות*. המלצה: לא להזין מידע רפואי.
- **SQLite:** כותב יחיד — מספיק ליחידה, לא ל-HA. נקודת מעבר מתוכננת.
- **אבטחה:** לפני פרודקשן — בדיקת חדירות, סקירת תצורת reverse proxy, `npm audit`.
- **נגישות:** בדיקה ידנית עם קורא מסך (NVDA/VoiceOver) על ידי מורשה נגישות.

### 13.1 MFA (TOTP)
- RFC 6238 (30 שניות, 6 ספרות, SHA-1 — תאימות לכל אפליקציות האימות). מימוש עם `node:crypto`, ללא ספרייה.
- הסוד מוצפן במנוחה (AES-256-GCM, מפתח `MFA_ENCRYPTION_KEY` מה-env). מניעת שימוש חוזר בקוד (replay) — שמירת ה-time-step האחרון.
- 10 קודי שחזור חד-פעמיים, נשמרים כ-hash בלבד, מוצגים פעם אחת.
- זרימה: סיסמה נכונה → אסימון ביניים (5 דק', עד 5 ניסיונות, נשמר כ-hash) → קוד → Session.
- `MFA_REQUIRED_ROLES=admin`: משתמש בתפקיד כזה ללא MFA מופנה להרשמה (כמו סיסמה זמנית).
- מנהל מערכת יכול לאפס MFA למשתמש (נרשם ביומן). ביטול עצמי דורש סיסמה + קוד.

### 13.2 התראות
- **במערכת:** פעמון עם מונה; התראה כשמשייכים אותך לפריט, ותזכורת יומית על פריטים שלך שבאיחור / ביעד מחר.
- **דוא"ל (אופציונלי):** אותן התראות; ריכוז יומי בשעה מוגדרת (`DIGEST_HOUR`). כל משתמש יכול לכבות דוא"ל בפרופיל.
- תוכן הדוא"ל מינימלי: שם הפריט, הלוח וקישור — ללא תוכן טקסט חופשי (מזעור מידע).
- שמירה: 90 יום, ואז מחיקה אוטומטית.

### 13.3 קבצים מצורפים
- סוגים מותרים: PDF, PNG, JPEG, WEBP, DOCX, XLSX — אימות לפי **חתימת תוכן (magic bytes)** ולא רק סיומת.
- עד 10MB לקובץ, 20 קבצים לפריט, rate-limit להעלאות. שם הקובץ בדיסק = UUID, ללא סיומת, מחוץ ל-web root.
- מצבים: `pending` (הסגר) → `clean` / `infected` / `error`. רק `clean` ניתן להורדה. קובץ נגוע נמחק מהדיסק, נרשם ביומן אבטחה, והמשתמש מקבל הודעה כללית.
- סריקה: פרוטוקול clamd INSTREAM (TCP/Unix socket) ממומש ישירות. אין סורק → fail-closed.
- הורדה: `Content-Disposition: attachment`, `nosniff`, `CSP: sandbox`, הרשאת צופה בלוח.
- הרשאות: עורך מעלה; מוחק — מי שהעלה או בעלי הלוח.
- שיוך אנשים לפריט מוגבל לחברי הלוח (או מנהלי מערכת) — כדי שמי שמקבל התראה אכן יכול לפתוח את הפריט.

### 13.4 ייצוא
- `GET /api/boards/:id/export.csv` (צופה ומעלה): UTF-8 עם BOM (עברית תקינה באקסל), תוויות במקום מזהים, תאריכים DD/MM/YYYY.
- הגנה מפני CSV/Formula injection: תאים שמתחילים ב-`= + - @` טאב או CR מקבלים תחילית `'`.
- נרשם ביומן אבטחה (ייצוא נתונים).

### כללי ריצה (בטיחות המנוע)

1. **ללא שרשור:** שינוי שבוצע ע"י אוטומציה אינו מפעיל אוטומציות נוספות — אין לולאות אינסופיות.
2. החוק רץ **אחרי** שהשינוי של המשתמש נשמר, בטרנזקציה נפרדת; כשל בחוק נרשם ביומן ההרצות ולעולם לא מכשיל את פעולת המשתמש.
3. כל ערך שהחוק כותב עובר **אותה ולידציה** כמו עריכה ידנית (עמודה קיימת, תווית קיימת, משתמשים חברי לוח). אם עמודה נמחקה — ההרצה נרשמת כשגיאה.
4. היסטוריית השינויים מציגה "אוטומציה «שם החוק»" כמבצע (ללא משתמש).
5. טריגרים מתוזמנים רצים פעם ביום אחרי `DIGEST_HOUR`, ופעם אחת לכל פריט (תאריך — פעם לכל יום יעד; SLA — פעם לכל כניסה לתווית).
6. נמעני התראה ודוח נבדקים **בזמן השליחה** — מי שאיבד גישה ללוח לא יקבל דבר.
7. פריט חוזר: אם השרת היה כבוי וכמה מועדים עברו — נוצר **מופע אחד** (לא הצפה), והמועד הבא מחושב קדימה.

### אבטחה ופרטיות

- כל נתיב: אימות + `AccessService` (404 ללא גישה) + Zod. ICS: `Content-Disposition: attachment`, escape לפי RFC 5545, ללא תיאור חופשי — רק שם פריט וקישור.
- **אין קישור מנוי (subscription URL) ליומן** — היה מחייב כתובת עם אסימון שעובדת בלי התחברות, בניגוד להחלטה "הכל מאחורי התחברות". אפשרי בעתיד באישור.
- דוא"ל דוח: שם לוח, שמות פריטים, ספירות וקישור — ללא תוכן טקסט חופשי (מזעור מידע). מכבד את ביטול התראות הדוא"ל בפרופיל.

## 19. התחברות ארגונית (SSO) וסנכרון משתמשים (SCIM) — אפיון

**החלטה (10/11/2026):** SSO + SCIM בלבד מגל F. **התחברות רגילה (דוא"ל + סיסמה) נשארת פעילה עד שה-SSO יוגדר**; שאר גל F נדחה.

| # | פיצ'ר | פירוט |
|---|------|-------|
| F1 | **SSO ב-OpenID Connect** | Microsoft Entra ID (או כל ספק OIDC): Authorization Code + PKCE, `state` + `nonce`, אימות חתימת ID Token, מנפיק וקהל (ספריית `openid-client`). כפתור "התחברות ארגונית" בעמוד הכניסה. קישור משתמש: מזהה ייחודי מהספק (`oid`/`sub`) → ובכניסה הראשונה לפי דוא"ל. משתמש שאין לו חשבון — נדחה (אלא אם הופעל יצירה אוטומטית, `SSO_JIT_PROVISIONING`), עם הגבלת דומיינים אופציונלית |
| F2 | **מדיניות התחברות רגילה** | `LOCAL_LOGIN`: `enabled` (ברירת מחדל) / `admins_only` (חשבון חירום למנהלי מערכת) / `disabled`. **לא ניתן לחסום התחברות רגילה כל עוד SSO לא מוגדר** (השרת מסרב לעלות) |
| F3 | **MFA עם SSO** | ברירת מחדל: ה-MFA נאכף אצל ספק הזהות (Conditional Access). אם הספק מדווח `amr` עם `mfa` — נחשב אימות דו-שלבי; אחרת, למי שהפעיל TOTP במערכת — נדרש גם קוד מקומי. `SSO_TRUST_IDP_MFA=true` סומך על מדיניות הספק בלי לבדוק `amr` |
| F4 | **SCIM 2.0** | `/scim/v2/Users` (+ `ServiceProviderConfig`, `ResourceTypes`, `Schemas`): יצירה, עדכון (PUT/PATCH), השבתה (`active=false` או DELETE — **השבתה, לא מחיקה**, כדי לשמור היסטוריה), חיפוש `userName eq`. אסימון Bearer (`SCIM_TOKEN`, ≥ 32 תווים), rate-limit. משתמשים מ-SCIM נוצרים בתפקיד `member`, ללא סיסמה (כניסה ב-SSO בלבד); תפקידים נקבעים במערכת ע"י מנהל. השבתה מבטלת את כל הסשנים מיד. **קבוצות (Groups) — לא בשלב זה** |

### אבטחה

- קובץ ה-`client secret` ו-`SCIM_TOKEN` — משתני סביבה בלבד. ה-redirect URI מחושב מ-`PUBLIC_URL` (לא מהבקשה).
- `state`/`nonce`/`code_verifier` נשמרים בשרת (טבלה, 10 דק', שימוש חד-פעמי); בדפדפן רק מזהה אקראי בעוגייה `sb_sso` (HttpOnly, Secure, SameSite=Lax — הכרחי כי החזרה מהספק היא ניווט מאתר אחר), נמחקת מיד.
- אחרי הצלחה: הפניה דרך דף ביניים באותו מקור (כך שעוגיית הסשן `SameSite=Strict` נשלחת), ל-`next` שעבר בדיקת נתיב פנימי.
- יומן אבטחה: `sso_login_success`, `sso_login_failed` (סיבה), `scim_user_created/updated/deactivated`.
- נקודות SCIM מחוץ ל-`/api` (ללא עוגיות; CSRF לא רלוונטי), מאומתות באסימון בלבד בהשוואה בזמן קבוע.

### נתונים (מיגרציה 8)

`users.sso_subject` (ייחודי), `users.auth_source` (`local`/`sso`/`scim`), `users.scim_external_id`; טבלת `sso_states`.

### החלטות תכנון (ניתן לשנות)

- **התראות מעקב בתוך המערכת + דוא"ל לפי העדפת המשתמש**, תוכן הדוא"ל: שם פריט ולוח בלבד (כמו היום). אין הודעה על שינוי שעשה המשתמש עצמו, ואין הודעה על שינויי אוטומציה.

- **User-Agent** כבר נשמר בסשן (200 תווים); מוצג כ"דפדפן · מערכת" בלבד. כתובת IP אינה נשמרת בסשן ואינה מוצגת.
- תגובות-אימוג'י מסט קבוע בלבד (ללא קלט חופשי), כך שאין צורך בסניטציה ואין "הודעות נסתרות".
- **Escape בתוך חלון:** רכיב פנימי שטיפל ב-Escape (בורר, תפריט, עורך תא, טופס תשובה) סוגר רק את עצמו; החלון כולו נסגר רק ב-Escape נוסף (תוקן מרכזית ב-`Dialog`, כולל באג קיים בבוררי אנשים בתוך חלון הפריט).

## 22. איפוס סיסמה עצמי ("שכחתי סיסמה") — אפיון

**קיים:** איפוס ע"י מנהל מערכת (סיסמה זמנית + החלפה בכניסה הבאה); `create-admin --email …` למנהל שננעל. **חדש:** איפוס עצמי בדוא"ל.

| שלב | התנהגות |
|-----|---------|
| בקשה | בעמוד הכניסה "שכחתי סיסמה" ← דוא"ל ← **תמיד אותה הודעה** ("אם הכתובת רשומה ומורשית — יישלח קישור"), בלי לחשוף אם החשבון קיים |
| קישור | אסימון אקראי (256 ביט), נשמר **רק כ-hash**, תקף **30 דקות**, **חד-פעמי**; בקשה חדשה מבטלת קודמות. הקישור בפרגמנט (`/reset-password#token=…`) — לא נשלח לשרת בטעינת העמוד, לא נרשם ביומני proxy ולא דולף ב-Referer |
| איפוס | סיסמה חדשה (אותה מדיניות) ← כל החיבורים הפתוחים מנותקים, הנעילה מתאפסת, דוא"ל "הסיסמה שונתה". **אימות דו-שלבי לא מתבטל** — הכניסה הבאה עדיין דורשת קוד |
| מי זכאי | משתמש פעיל עם התחברות בסיסמה מותרת (`LOCAL_LOGIN`: הכל / מנהלי מערכת בלבד / אף אחד). משתמשי SSO/SCIM כשה-SSO מוגדר — לא (מתחברים דרך הארגון) |
| הגבלות | 5 בקשות ל-15 דק' לכל כתובת IP; לכל משתמש — לכל היותר קישור אחד ל-2 דקות ו-5 ביום; ניסיונות איפוס — 10 ל-15 דק' |
| בלי דוא"ל מוגדר | הקישור לא מוצג; במקומו "שכחת סיסמה? פנו למנהל המערכת" |
| יומן אבטחה | `password_reset_requested`, `password_reset` (+ כישלון אסימון) — בלי האסימון ובלי הדוא"ל המלא |

נתונים (מיגרציה 11): `password_resets (id = sha256(token), user_id, created_at, expires_at, used_at)`; ניקוי שעתי.
API: `POST /auth/password/forgot` (ציבורי), `POST /auth/password/reset` (ציבורי, באסימון).

| L4 | **הודעת סיום** | טקסט מותאם שמוצג אחרי שליחה (למשל "נחזור אליך תוך יומיים") |
| L5 | **חיבור לתהליך: התראה** | בחירת חברי לוח שמקבלים התראה (במערכת + דוא"ל לפי העדפה) על כל תשובה חדשה |
| L6 | **חיבור לתהליך: שיוך אוטומטי** | כל תשובה משויכת אוטומטית לאחראי/ם שנבחרו (עמודת האנשים הראשונה בלוח) — מופיעה מיד ב"המשימות שלי" שלהם |

כבר קיים ומשתלב: אוטומציות על "פריט נוצר" (למשל העברה לקבוצה, SLA), דשבורדים על לוח התשובות, ייצוא CSV / Excel.

החלטות: מקבלי התראה ומשויכים — רק חברי הלוח (נבדק בשמירה ושוב בשליחה). תנאי תצוגה נבדק גם בשרת. **אינטגרציה למערכות חיצוניות (Webhook ל-Teams / Power Automate, הטמעה באתר אחר) אינה חלק מהגל** — מחייבת החלטת אבטחה (יציאה לרשת, SSRF, סודות).

נתונים: בתוך `forms.config` (JSON) — אין מיגרציה. API: `GET /forms/managed`, `POST /forms/:id/duplicate`.

## 28. מפתחות גישה — Passkeys (אפיון)

**מטרה:** כניסה בלי סיסמה, עם טביעת אצבע / זיהוי פנים / קוד הנעילה של המכשיר (WebAuthn / FIDO2), בנוסף לסיסמה ול-SSO — לא במקומם.

**User stories**
- כמשתמש, אני מוסיף מפתח גישה מהפרופיל (אחרי אישור הסיסמה הנוכחית) ונכנס בפעם הבאה בלחיצה אחת, בלי דוא"ל וסיסמה.
- כמשתמש, אני רואה את המפתחות שלי (שם, מתי נוסף, שימוש אחרון, האם מסונכרן) ומוחק מפתח של מכשיר שאבד.
- כמנהל מערכת, "ניתוק מכשירים" של משתמש אחר מוחק גם את מפתחות הגישה שלו.

**החלטות**
| נושא | החלטה | חלופה שנדחתה |
|---|---|---|
| ספרייה | `@simplewebauthn/server` 14.0.3 + `@simplewebauthn/browser` 14.0.0 (גרסאות נעוצות) | מימוש עצמי של CBOR/COSE — סיכון קריפטוגרפי מיותר |
| סוג מפתח | Discoverable (`residentKey: required`), `userVerification: required`, `attestation: none` | Attestation — מזהה דגם מכשיר (פרטיות), לא נדרש כאן |
| MFA | כניסה במפתח גישה עם אימות משתמש נחשבת רב-שלבית (החזקה + ביומטרי/קוד) ואינה דורשת קוד TOTP | דרישת TOTP נוסף — חיכוך בלי תוספת אבטחה ממשית |
| הוספה | רק ממשתמש מחובר; חשבון מקומי מאשר את הסיסמה הנוכחית; עד 10 מפתחות | הוספה בלי אימות מחדש — סשן גנוב היה הופך לגישה קבועה |
| RP ID | שם המתחם של `PUBLIC_URL`; Origin מדויק של `PUBLIC_URL` | — |
| מדיניות SSO | `LOCAL_LOGIN=disabled` מכבה גם מפתחות גישה; `admins_only` — למנהלי מערכת בלבד | — |

**סכמה (מיגרציה 14):** `passkeys` (מפתח ציבורי, מונה חתימות, שם, זמנים), `webauthn_challenges` (חד-פעמי, 5 דקות, המזהה נשמר כ-hash), `sessions.via_passkey`.

**API:** `POST /auth/passkey/login/options|verify` (ציבורי, מוגבל קצב) · `GET /auth/passkeys` · `POST /auth/passkeys/register/options|verify` · `DELETE /auth/passkeys/:id`.

**מגבלות ידועות**
- מפתח הגישה קשור למתחם (`dreadlist.com`) ולא לתיקייה: אתר אחר באותו מתחם יכול טכנית לבקש חתימה מאותו מפתח. מומלץ תת-מתחם ייעודי בפרודקשן.
- שינוי שם המתחם ב-`PUBLIC_URL` מבטל את כל המפתחות הקיימים (המשתמשים נכנסים בסיסמה ומוסיפים מחדש).
- משתמש בתפקיד שמחייב MFA שנכנס **בסיסמה** עדיין נדרש ל-TOTP; המפתח פוטר רק כניסה שנעשתה במפתח.
- אין הודעת דוא"ל על הוספת מפתח (נרשם ביומן האבטחה בלבד).

## 29. גל N — חישובים ושכפול (אפיון)

**מטרה:** שתי יכולות שנמכרות בדרך כלל בחבילות בתשלום וחסרות למי שמנהל רשימות ציוד, תקציב ולוחות שנתיים.

### N1 — עמודת נוסחה
- סוג עמודה חדש `formula`: מחושבת מהתאים של אותו פריט, לקריאה בלבד, **לא נשמר ערך** (מחושב בזמן הצגה ובייצוא).
- שפה קטנה ובטוחה (`packages/shared/src/formula.ts`): מנתח רקורסיבי משלנו — **בלי `eval`**, בלי גישה לשום דבר מלבד תאי הפריט. מגבלות: 500 תווים, 200 צמתים, עומק 30.
- תחביר: `{שם עמודה}`, `+ − * /`, השוואות, טקסט במירכאות, `&` לחיבור. פונקציות: `IF AND OR NOT ROUND ABS MIN MAX SUM AVG DAYS TODAY EMPTY CONCAT`.

- נשמר לפי **מזהה עמודה** (שינוי שם עמודה לא שובר); העורך מציג כותרות. בתבנית לוח / שכפול — לפי מיקום (`{#n}`) ומוצמד מחדש.
- מופיע ב: טבלה, מגירת פריט, מיון, שורת סיכום קבוצה (סה"כ / ממוצע), ייצוא CSV / Excel, כרטיס QR.
- הגדרה: בעלי הלוח בלבד (כמו כל עמודה). אימות בשרת מול עמודות הלוח.

**מגבלות ידועות:** נוסחה אינה יכולה להסתמך על נוסחה אחרת (מונע מעגלים); אין נוסחאות על עמודות אנשים / צ'קליסט; אין סינון, אוטומציה או ווידג'ט דשבורד לפי תוצאת נוסחה; `TODAY()` לפי שעון הדפדפן בתצוגה ולפי אזור הזמן של השרת בייצוא.

### N2 — שכפול קבוצה
`POST /groups/:id/duplicate` (עורך): קבוצה חדשה "(עותק)" עם כל הפריטים ותתי-הפריטים. עד 2,000 פריטים. העתקה מרוכזת — **בלי התראות ובלי הפעלת אוטומציות**.

### N3 — שכפול לוח
`POST /boards/:id/duplicate` (בעלי הלוח שמורשה ליצור לוחות): קבוצות + עמודות (כולל נוסחאות), ולפי בחירה גם הפריטים. **לא מועתקים:** חברים, שיוך לאנשים, תוצאות צ'קליסט, עדכונים, קבצים, אוטומציות, טפסים. נרשם ביומן האבטחה (`board_duplicated`).

## 30. גל O — קישור בין פריטים ולוחות (אפיון)

**מטרה:** לחבר ידנית פריט לפריטים אחרים — גם בלוח אחר (אירוע ↔ פעולות מתקנות, ציוד ↔ בדיקות) — ולראות בטבלה כמה מהמקושרים כבר בוצעו.

- **O1 קישור ידני** (`kind: related`) על גבי טבלת `item_links` הקיימת (שעד היום שימשה רק קישורים אוטומטיים מצ'קליסט ומתחקיר).
  - הוספה: עורך בלוח של הפריט + לפחות צפייה בלוח של היעד. יעד שאין אליו גישה נענה כ"לא נמצא" (בלי לחשוף קיום).
  - הסרה: עורך באחד משני הלוחות. קישורים אוטומטיים אינם ניתנים להסרה ידנית.

- **מגבלות:** אין עמודת "מראה" שמציגה ערך של עמודה מהפריט המקושר (רק התקדמות); אין מיון / סינון לפי העמודה; שכפול לוח אינו מעתיק קישורים.

## 31. גל P — תאריך dd/mm/yyyy, הסתרת התפריט ומודולריות (אפיון)

### P1 — תאריך תמיד dd/mm/yyyy
שדה התאריך של הדפדפן מוצג לפי שפת הדפדפן (דפדפן באנגלית-ארה"ב ← mm/dd/yyyy), ואין דרך לשנות זאת מהאתר. לכן רכיב משלנו, `components/DateField.tsx`, בכל 11 שדות התאריך:
- שדה טקסט שמציג ומקבל dd/mm/yyyy; הקלדת ספרות ברצף מוסיפה לוכסנים; מתקבלים גם `7.3.27`, `7-3-2027` ו-ISO.
- כפתור לוח שנה פותח את בורר התאריכים של הדפדפן (נגיש ומוכר, בלי ספריית צד שלישי).
- תאריך לא אפשרי (31/02) מוסבר במילים ואינו נשמר; Esc מחזיר את הערך השמור; `min` / `max` נאכפים.
- תזכורת אישית: תאריך + בחירת שעה ב-24 שעות (במקום `datetime-local`).

### P2 — הסתרת התפריט הצדדי
כפתור התפריט בכותרת מופיע גם במסך רחב: מסתיר / מציג את התפריט, והלוח מקבל את כל הרוחב. הבחירה נשמרת בדפדפן (`localStorage`, העדפת תצוגה בלבד — לא מידע אישי). בטלפון הכפתור ממשיך לפתוח את התפריט כמגירה.

### P3 — מודולריות
- **רישום מודולים אחד** (`packages/shared/src/modules.ts`): מפתח, שם, תיאור ונתיבי ה-API של כל מודול אופציונלי — טפסים, דשבורדים, עומס צוות, מבט מנהל, הדרכות, נהלים, תאימות. הליבה (לוחות, פריטים, המשימות שלי, התראות, משתמשים, אבטחה) פעילה תמיד.
- **מנהל מערכת מכבה / מפעיל מודול** (מסך "מודולים"). מודול כבוי: נעלם מהתפריט ומחלון הפקודות של כולם, הכתובת שלו מציגה הסבר, **וה-API שלו עונה 404 בשרת** (לא רק הסתרה בממשק), והמשימות המתוזמנות שלו אינן רצות. הנתונים נשמרים וחוזרים בהפעלה מחדש.
- **רישום ניווט אחד בצד הלקוח** (`apps/web/src/modules/registry.ts`): התפריט, חלון הפקודות ושומרי הנתיבים (`ModuleGate`) נבנים מאותה רשימה. הוספת אזור חדש = רשומה אחת + הנתיבים שלו.
- מיגרציה 16: `app_settings` (הגדרות מערכת כ-JSON). מפתח לא מוכר מתעלמים ממנו, ומודול חדש פעיל כברירת מחדל — בלי מיגרציה נוספת.
- **מגבלות:** כיבוי "טפסים" אינו מסיר את עמודות / לוחות התשובות (הם לוחות רגילים); ווידג'טים בלוח הבקרה הראשי שמציגים נתוני מודול כבוי אינם מוסתרים אוטומטית; אין כיבוי ברמת לוח או משתמש.

## 32. גל Q — השלמת פערים מול השימוש בפועל: חיבור לוחות ועמודת מראה (אפיון)

**מקור:** מבנה הלוחות שהיחידה בנתה בעצמה במערכת הקיימת (ציוד, ביקורות, תקלות, אנשי תחזוקה, מנהלי מעבדה, חוקר ראשי) — נקרא לקריאה בלבד דרך החיבור לחשבון, בלי להעתיק נתונים. סוגי העמודות שם: טקסט, סטטוס, תאריך, מספר, טקסט ארוך, תת-פריטים, קבצים, **חיבור לוח** ו**מראה**; ואוטומציות "X ימים לפני / אחרי תאריך ← דוא"ל".

| בשימוש אצלכם | אצלנו לפני הגל | אחרי הגל |
|---|---|---|
| עמודת חיבור ללוח אחר (תקלה ← ציוד, ציוד ← אנשי תחזוקה) | קישור ידני במגירה בלבד | ✅ עמודת `relation` |
| עמודת מראה (מייל אנשי התחזוקה מהפריט המחובר) | ⬜ | ✅ עמודת `mirror` |
| עמודת קבצים (תמונות) | קבצים ברמת הפריט + גלריה | 🟡 ללא שינוי — אין עמודה ייעודית |
| תזכורת בדוא"ל לפני / אחרי תאריך | אוטומציות תאריך + התראות | 🟡 קיים; תבנית דוא"ל חופשית עם שדות — לא |
| "תאריך ביקורת אחרונה מתעדכן אוטומטית" | מודול תאימות מקדם תאריך אחרי בדיקה | ✅ קיים |
| תת-פריטים, QR לפריט, טופס דיווח | ✅ | ✅ |

### Q1 — עמודת "חיבור ללוח אחר" (`relation`)
- הגדרה: לוח יעד אחד (בעל הלוח, שחייב גישה ללוח היעד). בכל תא בוחרים עד 20 פריטים מהלוח המחובר, מרשימה עם חיפוש.
- נשמר ב-`item_links` עם `column_id` (מיגרציה 17), לא בתא עצמו. מחיקת העמודה מוחקת את החיבורים שלה.
- מי שאין לו גישה ללוח המחובר **אינו רואה** את שמות הפריטים ואינו יכול לשנות את החיבור. עריכה: עורך בלוח הזה + לפחות צפייה בלוח המחובר.
- בטבלה: שמות הפריטים; במגירה: קישורים לפריטים; בייצוא: שמות מופרדים ב-`;`.

### Q2 — עמודת "מראה" (`mirror`)
- הגדרה: עמודת חיבור של הלוח + עמודה של הלוח המחובר. מציגה את ערך העמודה מכל פריט מחובר, מחושב בזמן טעינה (תמיד עדכני), לקריאה בלבד.
- אותה הגנת הרשאות: בלי גישה ללוח המחובר — אין ערך.
- שכפול לוח / תבנית: ההפניה לעמודת החיבור נשמרת לפי מיקום ומוצמדת מחדש.

**מגבלות:** מראה היא טקסט בלבד (אין מיון / סינון / נוסחה עליה, ואין סיכום מספרי); אין חיבור דו-כיווני אוטומטי (בלוח היעד החיבור נראה ב"פריטים מקושרים" במגירה, לא כעמודה); אי אפשר לשנות את לוח היעד של עמודה קיימת — מוחקים ויוצרים מחדש.

## 33. גל R — פערים מתוך ניתוח המערכת הקיימת (אפיון)

מקור: `docs/GAP_ANALYSIS.md`. שלושה פערים שאינם דורשים שינוי ארכיטקטוני:

- **R1 סינון מתקדם** — `config.filter = { match: all | any, rules[] }` בתצוגה. מנוע משותף (`packages/shared/src/filters.ts`) עם אופרטורים לפי סוג עמודה: בחירה (אחד מ / אינו אחד מ), טקסט (מכיל), מספר ונוסחה (= > <), תאריך (עבר, בימים הקרובים / האחרונים, לפני / אחרי / בתאריך), תיבת סימון, ריק / אינו ריק. עד 10 תנאים. תנאי על עמודה שנמחקה אינו מסתיר דבר. נשמר ב"שמירה כתצוגה" (מאומת בשרת).
- **R2 סוללת סטטוס** בשורת הסיכום של כל קבוצה: פס צבעוני עם חלוקת התוויות, ותיאור טקסטואלי לקורא מסך.
- **R3 מחיקת תווית בשימוש**: השרת מסרב (400) אלא אם נשלח `replaceOptions` — לאיזו תווית להעביר, או `null` לניקוי מכוון. בממשק: שאלה מפורשת לכל תווית שהוסרה, עם מספר הפריטים; אי אפשר לשמור בלי החלטה. **שינוי התנהגות:** עד עכשיו ערכים נוקו בשקט.

**מגבלות:** הסינון רץ בדפדפן על פריטי הלוח (לא משפיע על ייצוא או על דשבורדים); אין סינון על עמודות חיבור / מראה / צ'קליסט / סיכון; אין Group by.

## 34. גל S — עדכונים מעוצבים ועמודת קבצים (אפיון)

- **S1 עיצוב בעדכונים.** העדכון נשמר כ**טקסט רגיל** עם סימון קל — `**מודגש**`, `*נטוי*`, `` `קוד` ``, שורות "- " / "1. " לרשימות — ומוצג כרכיבי React (`components/RichText.tsx`). **לא נשמר ולא מוצג HTML**, ולכן אין מה לנקות ואין XSS: `<img onerror>`, `<script>` ו-`javascript:` נשארים טקסט. רק כתובות `http(s)` הופכות לקישור (`rel="noopener noreferrer nofollow"`, לשונית חדשה). סרגל עיצוב מעל שדה העדכון (מודגש, נטוי, רשימות). בדוא"ל ובחיפוש הסימון מופיע כפי שנכתב.
- **S2 עמודת קבצים** (`files`, לקריאה בלבד): מספר הקבצים בפריט (בלי קבצים שנמצאו נגועים); לחיצה פותחת את הפריט. מופיעה בייצוא. הקבצים עצמם נשארים ברמת הפריט (לשונית "קבצים") — אין אחסון נפרד לכל עמודה.
- **מגבלות:** אין עיצוב בתשובות בשרשור מעבר לאותו סימון (אין שם סרגל); אין טבלאות / תמונות מוטמעות בעדכון; עמודת הקבצים אינה מפרידה בין סוגי קבצים.

## 35. גל T — קיבוץ שורות, שם לשורה ותווית שיצאה משימוש (אפיון)

- **T1 קיבוץ לפי (Group by).** בתצוגת הטבלה אפשר לקבץ את השורות לפי עמודת סטטוס או אנשים במקום קבוצות הלוח (`config.groupBy`, נשמר בתצוגה). מקטע לכל תווית / אדם שיש לו פריטים, ועוד "ללא…". פריט עם כמה אחראים מופיע אצל כל אחד מהם. במצב מקובץ אין שורת "פריט חדש" ואין שינוי שם קבוצה (המקטעים מחושבים); סיכום הקבוצה, מיון, סינון ובחירה מרובה ממשיכים לעבוד.
- **T2 שם לשורה.** לכל לוח אפשר להגדיר איך נקראת שורה ("פריט ציוד", "ביקורת") — מיגרציה 18, `boards.item_term`. מופיע בשדה ההוספה ("+ הוספת ביקורת"). מונה הפריטים נשאר "פריטים" (אין דרך אמינה לרבים בעברית).
- **T3 תווית "לא לבחירה".** תווית שיצאה משימוש נשארת בפריטים שכבר מסומנים בה, אך אינה מוצעת עוד בתאים (סטטוס ותגיות). זו לא מחיקה — אין צורך בהחלטה על פריטים. **מגבלה:** האכיפה בממשק בלבד; ה-API עדיין מקבל את התווית (היא תקינה), כך שאוטומציות וייבוא יכולים להמשיך להשתמש בה.
- **לא נבנה:** עמודת כפתור — דורשת טריגר חדש במנוע האוטומציות ("כפתור נלחץ"); נדחה.

## 36. אישור מראש (12.11.2026) ותוכנית הגלים U–Z

בעל המערכת אישר מראש את ההצעות שחיכו לאישור ב-`docs/GAP_ANALYSIS.md`. סדר הביצוע, מהפשוט והבטוח למורכב:

| גל | נושא | עיקרי ההחלטות |
|---|---|---|
| **U** | סביבות עבודה | סידור בלבד — **לא נותנות הרשאות**; אין תיקיות בשלב זה |
| V | נעילת עריכה לעמודה ("רק בעלי הלוח עורכים") | אכיפה בשרת בכל נתיבי הכתיבה. הסתרת עמודה מצפייה — נדחית: יותר מדי נתיבי דליפה (היסטוריה, ייצוא, חיפוש, נוסחה, מראה) |
| W | Webhooks יוצאים | HTTPS בלבד, חתימת HMAC, חסימת כתובות פנימיות (SSRF), יומן מסירות, בעל הלוח בלבד |
| X | אסימוני API אישיים | נשמר hash בלבד, הרשאות המשתמש עצמו, ניתן לביטול, נרשם ביומן |
| Y | מעקב זמן | **דורש בדיקת פרטיות** (שעות עבודה של עובדים) — כבוי כברירת מחדל כמודול |
| Z | אורחים חיצוניים + תבנית מערך הביקורות | אורח = חשבון עם התחברות, רואה רק לוחות שהוזמן אליהם, בלי ספריית משתמשים |

### גל U — סביבות עבודה (אפיון)
- מיגרציה 19: `workspaces` + `boards.workspace_id` (מחיקת סביבה ← `NULL`, הלוחות נשארים).
- **אין משמעות הרשאתית:** מי רואה לוח נקבע רק לפי חברי הלוח. שם סביבת עבודה גלוי רק למי שרואה לפחות לוח אחד בה, ולמנהלים (שמסדרים).
- יצירה / שינוי שם / מחיקה: מנהלים ומנהלי מערכת (עד 50, שם ייחודי). שיוך לוח: בעל הלוח (בהגדרות הלוח או ביצירה). לוח משוכפל נשאר באותה סביבה.
- ממשק: עמוד "לוחות" והתפריט הצדדי מקובצים לפי סביבת עבודה; "ללא סביבת עבודה" בסוף.
- **מגבלות:** (תיקיות בתוך סביבה נוספו בגרסה 1.15.0, ראו §39); אין סדר ידני של סביבות (לפי סדר היצירה); אין "סביבה סגורה" — הרשאות נשארות ברמת הלוח.

### גל V — נעילת עריכה לעמודה (אפיון)
- הגדרת עמודה `editBy: 'owners'` — רק בעלי הלוח משנים את התאים שלה; עורכים רואים אותה לקריאה בלבד.
- **אכיפה בשרת** (`ItemService.assertMayEditColumns`) בכל נתיב שאדם מפעיל: עריכת פריט, יצירת פריט עם ערך, עריכה מרובה, ייבוא, בחירת פריטים בעמודת חיבור, והעברת פריט ללוח אחר (ערכים אינם נוחתים בעמודה נעולה). שחזור מהיסטוריה עובר דרך עריכה רגילה ולכן נאכף.
- **לא נחסמים בכוונה:** אוטומציות וטפסים — אותם הגדיר בעל הלוח, והם אינם "אדם שעורך".
- הנעילה היא הגדרה עצמאית: שמירת תוויות / נוסחה אינה מבטלת אותה; רק בעל הלוח נועל ופותח.
- **מה לא נבנה:** הסתרת עמודה מצפייה. הערך היה עלול לדלוף דרך היסטוריה, ייצוא, חיפוש, נוסחה, עמודת מראה, התראות וטפסים; עדיף לא להבטיח הסתרה שאינה אטומה. למידע שלא כולם צריכים לראות — לוח נפרד עם חברים אחרים ועמודת חיבור.

### גל W — Webhooks יוצאים (אפיון)
**מה:** בעל לוח רושם כתובת HTTPS שמקבלת הודעת JSON חתומה כשפריט בלוח נוצר או משתנה (למשל Power Automate / Teams דרך מחבר ארגוני).

**מידע שיוצא (Data minimisation):** מזהה ושם הלוח, מזהה / שם / קישור הפריט, ערכי העמודות **כטקסט** (כמו בייצוא), ורשימת העמודות שהשתנו. **לא יוצאים:** כתובות דוא"ל, מזהי משתמשים, עדכונים, קבצים, וערכים שמגיעים מלוח אחר (עמודות חיבור / מראה / מקושרים).

**בקרות**
| סיכון | בקרה |
|---|---|
| שליחת מידע בלי החלטה ארגונית | מודול **כבוי כברירת מחדל**; מנהל מערכת מפעיל אחרי אזהרה; רק בעל לוח מגדיר; נרשם ביומן (שם השרת בלבד — הנתיב עלול להכיל אסימון) |
| SSRF — שימוש בשרת כדי לגעת ברשת הפנימית | `lib/safeFetch.ts`: רק `https`, רק יציאה 443, בלי פרטי התחברות בכתובת; **כל** הכתובות שהשם נפתר אליהן חייבות להיות ציבוריות, והחיבור נעשה לאותה כתובת שנבדקה (מניעת DNS rebinding); חסומים loopback, פרטיות, link-local / metadata, CGNAT, IPv6 מקומיות וממופות; **אין מעקב אחר הפניות**; גוף התשובה לא נקרא; פסק זמן 5 שניות |
| זיוף הודעות אצל המקבל | חתימת HMAC-SHA256 על `timestamp.body`; הסוד מוצג **פעם אחת**, נשמר מוצפן (AES-GCM) |
| הצפה / מקבל תקול | תור סדרתי מחוץ לבקשת המשתמש; עד 5 Webhooks ללוח; כיבוי אוטומטי אחרי 10 כישלונות רצופים; יומן 30 מסירות אחרונות (תוצאה בלבד, בלי גוף ההודעה) |

**API:** `GET/POST /boards/:id/webhooks`, `PATCH/DELETE /webhooks/:id`, `GET /webhooks/:id/deliveries`, `POST /webhooks/:id/test`. מיגרציה 20.

**מגבלות:** (ניסיון חוזר נוסף בגרסה 1.13.0 — 30 שניות ו-5 דקות, אותו מזהה מסירה; הנמען צריך לסנן כפילויות לפי `X-SUBoard-Delivery`); אין אירוע מחיקה / עדכון (תגובה) / קובץ; ההודעות נשלחות מהשרת עצמו (אם יש חומת אש יוצאת — צריך לאפשר את היעד); אחרי אתחול השרת הודעות שהיו בתור אובדות.
**דורש בדיקה:** מדיניות אבטחת המידע של הארגון לגבי העברת מידע לשירות חיצוני, והסכם עיבוד מידע (DPA) מול ספק היעד אם מדובר במידע אישי.

### גל X — אסימוני API אישיים (אפיון)
**מה:** משתמש יוצר בפרופיל אסימון (`sbp_…`) שמאפשר לסקריפט לקרוא לאותו API שהממשק משתמש בו, עם הכותרת `Authorization: Bearer …`.

| נושא | החלטה |
|---|---|
| הרשאות | האסימון פועל כבעליו — **אף פעם לא יותר**: אותן בדיקות הרשאה בכל בקשה; איבוד גישה ללוח חל מיד גם על האסימון |
| היקף | `read` (GET בלבד, ברירת המחדל) או `write` |
| מה סגור לאסימון | כל `/auth/*` (סיסמה, MFA, מפתחות גישה, חיבורים, **אסימונים אחרים**), `/admin/*`, ניהול משתמשים, SCIM — גם לאסימון של מנהל מערכת |
| אחסון | נשמר **hash בלבד** (SHA-256); האסימון מוצג פעם אחת; 256 ביט אקראיים |
| תוקף | חובה: 30 / 90 / 365 יום; עד 5 אסימונים למשתמש |
| ביטול | ע"י הבעלים; "ניתוק מכשירים" ע"י מנהל מוחק גם אסימונים; חשבון מושבת / עם סיסמה זמנית — האסימון אינו פועל; כיבוי המודול — כל האסימונים מפסיקים לפעול |
| CSRF | בקשה עם אסימון ו**בלי** עוגיית סשן פטורה מבדיקות הדפדפן (אין אישור סביבתי לרכוב עליו); בקשה עם עוגייה נשארת מוגנת |
| הפעלה | מודול **כבוי כברירת מחדל**; מנהל מערכת מפעיל |
| תיעוד | יצירה וביטול ביומן האבטחה; "שימוש אחרון" מוצג לבעלים |

מיגרציה 21. **מגבלות:** אין אסימון ברמת לוח (רק אישי); אין הגבלת כתובות IP לאסימון; אין תיעוד API ציבורי נפרד — ה-API הוא זה של הממשק ואינו מובטח כיציב בין גרסאות; הגבלת הקצב היא הכללית (לפי כתובת).

### גל Y — מעקב זמן (אפיון)
**מה:** עמודת "מעקב זמן" (`time`): שעון התחלה / עצירה ורישום ידני של שעות ודקות; התא מציג את סך הזמן בפריט.

**פרטיות — זה מידע על זמן העבודה של עובדים:**
| החלטה | נימוק |
|---|---|
| מודול **כבוי כברירת מחדל**; גם יצירת העמודה חסומה עד ההפעלה | החלטה ארגונית, לא טכנית |
| **שום דבר לא נמדד אוטומטית** — רק מה שאדם מפעיל או מקליד | אין מעקב סמוי |
| כל חברי הלוח רואים את **הסך הכולל** בפריט; **מי רשם מה** — רק האדם עצמו ובעלי הלוח | מזעור חשיפה בין עמיתים |
| מי שרואה שעון פעיל של אחרים רואה רק **כמה** שעונים פועלים, לא של מי | כנ"ל |
| אדם מוחק רישומים שלו; בעל לוח מוחק כל רישום | תיקון טעויות |
| הרישומים נמחקים עם הפריט / הלוח / המשתמש | אין שמירה מעבר לצורך |

**התנהגות:** שעון אחד פועל לכל אדם (הפעלה בפריט אחר עוצרת את הקודם); שעון שנשכח נסגר ב-12 שעות; רישום ידני עד 12 שעות, לא בתאריך עתידי; צופים אינם רושמים זמן. מופיע בייצוא כ-`שעות:דקות`. כיבוי המודול מסתיר את הנתונים בלי למחוק אותם. מיגרציה 22.

**מגבלות:** אין דוח זמן מרוכז לפי אדם / תקופה (במכוון — זה כבר כלי פיקוח); אין סינון / מיון / נוסחה על העמודה; עריכת רישום קיים נוספה בגרסה 1.13.0 (רק הרישום של עצמך, ורק אחרי שהשעון נעצר).
**דורש בדיקה משפטית / ממונה פרטיות לפני הפעלה:** מעקב אחר זמן עבודה של עובדים (יידוע העובדים, מטרה, מידתיות), בהתאם לחוק הגנת הפרטיות ולהנחיות הרשות להגנת הפרטיות בנושא מעקב במקום העבודה.

## 38. גל AA — עמודות ואפשרויות חסרות (אפיון)

יכולות כלליות של מערכת ניהול עבודה (לפי §37 — בלי תהליכים ייעודיים לתחום).

### סוגי עמודות חדשים
| סוג | התנהגות |
|---|---|
| **שעה** (`hour`) | שעון 24 שעות `HH:MM`; מקבל גם `830` / `8.30`; שעה לא אפשרית מסומנת ואינה נשמרת |
| **שבוע** (`week`) | בוחרים יום כלשהו, נשמר ומוצג השבוע כולו (ראשון–שבת); נשמר כתאריך יום ראשון |
| **צבע** (`color`) | בחירה מפלטת הצבעים של המערכת, עם שם הצבע (לא צבע בלבד) |
| **הצבעה** (`vote`) | קול אחד לכל אדם; לחיצה נוספת מבטלת. אדם משנה **רק את הקול שלו** — נתיב ייעודי, לא עריכת תא; צופים אינם מצביעים |
| **נוצר בתאריך** (`created_at`) | תאריך ושעת יצירת הפריט, לקריאה בלבד |
| **כפתור פעולה** (`button`) | כפתור בשורה שקובע תווית בעמודת סטטוס של אותו לוח. הלחיצה היא עריכה רגילה: הרשאות, נעילת עמודה, היסטוריה, ביטול ואוטומציות חלים כרגיל |

### אפשרויות לעמודה קיימת ("אפשרויות" בהגדרות הלוח)
- **תיאור** — לכל עמודה; מוצג ככלי-עזר על הכותרת, נקרא ע"י קורא מסך אחרי הכותרת, ומופיע מתחת לשדה במגירת הפריט.
- **יחידה ומספר ספרות אחרי הנקודה** — לעמודות מספר ונוסחה (`₪1,234.50`, `12.5 ק"ג`); סימן מטבע לפני המספר, יחידה אחרת אחריו; חל גם בייצוא.
- **שינוי התנהגות:** עדכון הגדרות עמודה **ממזג** עם הקיים במקום להחליף — שמירת תוויות אינה מוחקת נעילה / תיאור / יחידה. לניקוי: תיאור ריק, יחידה ריקה, `decimals: null`, `editBy: 'editors'`.

### מה לא נבנה, ולמה
- **מיקום עם מפה** — מפה חיצונית שולחת כתובות לצד שלישי; עמודת טקסט מספיקה.
- **צוות** — אין במערכת ישות "צוות"; דורש אפיון נפרד.
- **מדינה, שעון עולמי, מסמך** — ערך נמוך למערכת פנימית.
- **רשימה נפתחת** — קיים כ"תגיות" (בחירה מרובה) ו"סטטוס" (בחירה אחת).
- ~~אין סינון / נוסחה על העמודות החדשות~~ — נסגר בגרסה 1.12.0 (ראו §39).

## 39. גל AB — סגירת מגבלות של גל AA (1.12.0)

המשתמש שאל אם אפשר לסדר את המגבלות שנרשמו. כן — עוברים עליהן לפי סדר, בתוך ההיקף של תחליף כללי למערכת ניהול עבודה.

### נסגר בגרסה 1.12.0
- **סינון מתקדם** על: שעה (שווה / אחרי / לפני), שבוע ותאריך יצירה (כל תנאי התאריך), צבע (בחירה), הצבעה ומספר קבצים (מספר), קישור ללוח ועמודת מראה (מכיל / אינו מכיל / ריק).

## 40. חשבונות אורח — נבנה בגרסה 1.17.0 (מודול כבוי כברירת מחדל)

> **הנחות עבודה שנבחרו** (המשתמש אישר מראש את הפיצ'ר ולא ענה על השאלות הפתוחות, ולכן נבחרה בכל שאלה האפשרות השמרנית): אורח יכול להיות צופה או עורך לפי החלטת בעל הלוח; רק מנהל מערכת יוצר אורח; תוקף ברירת מחדל 90 יום; אורח רואה את תוכן הלוח כפי שהוא (כולל היסטוריה); ייצוא סגור לאורחים לגמרי (בלי מתג לכל לוח). **שונה מהאפיון המקורי:** במקום ערך חדש ב-`users.role` (שהיה מחייב בנייה מחדש של טבלת המשתמשים) נוסף דגל `is_guest` — אורח הוא "חבר" עם דגל, והאכיפה היא ברשימת נתיבים מותרים (ברירת מחדל: סגור). הפיכת חשבון קיים לאורח או להפך אינה נתמכת — יוצרים חשבון חדש.
>
> **מגבלות ידועות:** אורח-עורך אינו יכול ליצור קבוצות או לשמור תצוגות; הדפסת המסך (PDF) אינה חסומה — רק קובצי הייצוא; אין הודעת מייל לפני פקיעה; SSO / SCIM אינם יוצרים אורחים.

**המטרה:** לתת לגורם חיצוני (קבלן, ספק, נציג מחלקה אחרת) גישה ללוח אחד או לכמה לוחות, בלי שיראה שום דבר אחר במערכת. ב-monday זה "Guest". אצלנו הכול מאחורי התחברות, ולכן אורח הוא **חשבון עם התחברות** ולא קישור ציבורי.

### מה אורח רואה ועושה
| נושא | אורח | חבר רגיל (להשוואה) |
|---|---|---|
| לוחות | רק לוחות שהוזמן אליהם במפורש | רק לוחות שהוא חבר בהם |
| תפקיד בלוח | צופה או עורך — **לעולם לא בעלים** | צופה / עורך / בעלים |
| ספריית המשתמשים | אין. רואה רק שמות של חברי הלוחות שהוא בהם, בלי כתובות מייל | שמות של כל המשתמשים |
| יצירת לוח / טופס / סביבת עבודה / תבנית | לא | לפי התפקיד |
| מודולים רוחביים (דשבורדים, עומס צוות, דוח חודשי, הדרכות, נהלים, תאימות) | לא | לפי המודול |
| חיבור ללוח אחר / עמודת מראה | רואה רק אם הוזמן גם ללוח המחובר (כבר כך היום) | אותו דבר |
| אסימוני API, webhooks | לא | לפי התפקיד |
| חיפוש כללי, "המשימות שלי", התראות | רק מתוך הלוחות שלו | רק מתוך הלוחות שלו |
| ייצוא לוח | רק אם בעל הלוח התיר לאורחים (ברירת מחדל: לא) | כן |

### אבטחה
- **תפקיד מערכת חדש `guest`** — נאכף בשרת בכל נקודת קצה, לא בהסתרת כפתורים. ברירת המחדל לכל נתיב חדש: סגור לאורח, אלא אם נפתח במפורש.
- **תוקף חובה:** לכל חשבון אורח תאריך תפוגה (ברירת מחדל 90 יום, מקסימום שנה). אחרי התפוגה ההתחברות נחסמת והסשנים מבוטלים; מנהל מערכת יכול להאריך.
- **מי מזמין:** מנהל מערכת בלבד יוצר חשבון אורח. בעל לוח מוסיף אורח קיים ללוח שלו.
- **אימות דו-שלבי:** חובה לאורח (כמו למנהלים), כי החשבון נגיש מחוץ לארגון.
- **זיהוי בממשק:** תג "אורח" ליד השם בכל מקום (חברי לוח, עדכונים, היסטוריה), כדי שלא יכתבו לידו מידע פנימי בטעות.
- **יומן ביקורת:** יצירה, הארכה, ביטול, הוספה ללוח והסרה ממנו.
- **הסרה:** ביטול אורח מבטל סשנים, מפתחות גישה (passkeys) ואסימונים, ומסיר אותו מכל הלוחות. מה שכתב נשאר, עם שמו.

### פרטיות
- אורח חשוף לשמות חברי הלוח ולתוכן הלוח — זו העברת מידע לגורם חיצוני. **דורש בדיקה משפטית** (חוק הגנת הפרטיות ותיקון 13; ואם האורח מחוץ לישראל — העברת מידע לחו"ל).
- נאסף על האורח: שם, מייל, ארגון (שדה חופשי, לא חובה), תאריך תפוגה. נמחק / עובר אנונימיזציה לפי אותה מדיניות שמירה של משתמש רגיל.
- יש לעדכן את `PRIVACY.md` ואת טבלת המידע האישי לפני הפעלה.

### מימוש (שלבים)
1. מיגרציה 24: `users.role` מקבל `guest`; `users.guest_expires_at`, `users.guest_org`; `boards.guests_may_export`.
2. שרת: בדיקת תפקיד מרכזית (`requireNotGuest`) על כל הנתיבים הרוחביים; ספריית משתמשים מצומצמת; חסימת בעלות; תפוגה בהתחברות ובכל בקשה; מודול `guests` כבוי כברירת מחדל.
3. ממשק: ניהול אורחים בעמוד המשתמשים (מנהל מערכת), תג "אורח", תפריט צד מצומצם.
4. בדיקות: מטריצת הרשאות מלאה (כל נתיב × אורח), תפוגה, IDOR בין לוחות, נגישות.

### שאלות פתוחות (נדרשת החלטה לפני בנייה)
1. האם אורח יכול **לערוך**, או צופה + תגובות בלבד?
2. האם בעל לוח רשאי ליצור אורח בעצמו, או רק מנהל מערכת? (ההצעה: רק מנהל מערכת.)
3. תוקף ברירת מחדל — 90 יום מתאים?
4. האם אורח רואה את **היסטוריית** הפריט ואת העדכונים שנכתבו לפני שהוזמן?
5. האם בכלל יש צורך — כלומר, יש היום גורמים חיצוניים שעובדים איתכם ב-monday כאורחים?

## 41. לוח פתוח לכל המשתמשים (1.18.0)

**הצורך:** ב-monday יש לוח "ראשי" שכל החשבון רואה. אצלנו כל לוח היה גלוי רק לחבריו, ולוח מודעות / נהלים כלליים חייב הוספה של כל משתמש בנפרד.

**מה נבנה:** `boards.open_role` (מיגרציה 25): ריק = חברי הלוח בלבד (ברירת המחדל), `viewer` או `editor` = כל משתמש פעיל שאינו אורח מקבל לפחות את התפקיד הזה. חבר לוח שומר על התפקיד הגבוה מבין השניים. לעולם לא "בעלים" — מבנה, הגדרות וחברים נשארים אצל הבעלים.

**אבטחה:**
- ההחלטה מתקבלת במקום אחד — `AccessService.boardRole` — ולכן חלה על כל נתיב, חיפוש, דשבורד והתראה בלי קוד נוסף.
- דגל האורח נקרא מהמסד בכל בדיקה, ולא מהקורא: גם קוד עתידי שישכח להעביר את הדגל לא יחשוף לוח פתוח לאורח.
- רק בעל הלוח פותח וסוגר; יש חלון אישור שמסביר מה ייחשף; הפעולה נרשמת ביומן האבטחה (`board_opened`).
- סגירה מחזירה מיד למצב "חברים בלבד".

**פרטיות:** פתיחת לוח חושפת את כל תוכנו (פריטים, עדכונים, קבצים, שמות האחראים) לכל העובדים. האחריות לבדוק שאין בלוח מידע רגיש היא של בעל הלוח — זה כתוב בחלון האישור.

**מגבלות:** בלוח פתוח אפשר לשייך כאחראי רק חברי לוח; אין "פתוח לסביבת עבודה מסוימת" — רק לכולם או לחברים.

## 42. צוותים (1.19.0)

**הצורך:** ב-monday יש צוותים ועמודת "צוות". אצלנו אפשר היה לשייך רק אנשים בודדים, והוספת מחלקה שלמה ללוח דרשה הוספה של כל אחד בנפרד.

**מה נבנה**
- מיגרציה 26: `teams` (שם ייחודי) ו-`team_members`.
- API: `GET /teams` (כל משתמש שאינו אורח), `POST /teams`, `PATCH|DELETE /teams/:id` (מנהלים), `POST /boards/:id/members/team` (בעל הלוח).
- עמוד "צוותים" (בתפריט למנהלים; קריאה בלבד לשאר).
- סוג עמודה `team`: מערך מזהי צוותים (עד 10); השרת מאמת שהצוותים קיימים; סינון מתקדם וייצוא.
- "הוספת צוות שלם" בהגדרות הלוח.

**החלטות אבטחה**
- **צוות אינו מעניק גישה.** הוספת צוות ללוח היא פעולה חד-פעמית של בעל הלוח שמוסיפה את האנשים כחברים רגילים — אין "חברות דינמית". כך מודל ההרשאות נשאר במקום אחד (חברי הלוח), ושינוי בצוות ע"י מנהל אחר אינו פותח לוח למישהו בלי ידיעת בעל הלוח.
- הוספת צוות אינה מורידה הרשאה של חבר קיים, ואי אפשר להוסיף צוות כ"בעלים".
- אורחים אינם יכולים להיות חברי צוות, ו-`/teams` אינו ברשימת הנתיבים המותרים לאורח — אורח רואה בתא רק כמה צוותים נבחרו.
- שינויים בצוותים נרשמים ביומן האבטחה (`team_changed`).

**מגבלות:** שיוך צוות בעמודה אינו שולח התראה לחבריו ואינו מופיע ב"המשימות שלי"; אין מיון לפי עמודת צוות; הסרת אדם מצוות אינה מסירה אותו מלוחות; SCIM אינו מסנכרן קבוצות לצוותים.
