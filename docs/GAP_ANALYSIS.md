# פערים מול מערכת ניהול העבודה הקיימת של היחידה

> בסיס: מסמך "איך המערכת הקיימת בנויה ועובדת" (12.11.2026, נכתב מתוך החשבון של היחידה, קריאה בלבד) + קריאת מבנה הלוחות דרך החיבור לחשבון.
> המסמך ממפה **יכולות** (מה המשתמשים רגילים שיש), לא עיצוב או קוד. SUBoard נבנה בעיצוב ובמבנה משלו.
> סטטוס: ✅ קיים · 🟡 חלקי · ⬜ חסר · 🚫 הוחלט שלא (עם הסיבה).

## 1. מבנה הנתונים
| במערכת הקיימת | ב-SUBoard | הערה |
|---|---|---|
| Workspace → Folder → Board | ✅ סביבות עבודה (גל U) + תיקיות (1.15.0) + מועדפים + "נפתחו לאחרונה" | סביבה ותיקייה מסדרות בלבד, לא נותנות הרשאות; רמה אחת של תיקיות |
| Groups כמיכל ויזואלי | ✅ | צבע, קיפול, שכפול קבוצה |
| Items + ערכים לפי סוג עמודה | ✅ | אימות לפי סוג בשרת |
| תת-פריטים בלוח נסתר נפרד (עמודות אחרות, "סטטוסים מתים") | ✅ אחרת בכוונה | אותן עמודות, אותו לוח, עד 5 רמות, התקדמות באב — ההחלטה שהמסמך ממליץ עליה |
| Updates, קבצים, יומן פעילות | ✅ | שרשור, אזכורים, תגובות, שחזור ערך מההיסטוריה |
| שם מותאם לשורה ("פריט ציוד") | ✅ (גל T) | בשדה ההוספה |
| מזהי עמודה יציבים, תווית עם מזהה נפרד מהטקסט | ✅ | נוסחאות ומראות נשמרות לפי מזהה |

## 8. API
Webhooks יוצאים ✅ ואסימוני API אישיים ✅ (שניהם מודולים כבויים כברירת מחדל). GraphQL ציבורי 🚫 — ה-API הוא REST של הממשק; אין התחייבות ליציבות בין גרסאות.

## 9. ההחלטות שהמסמך ביקש לקבל
1. **תת-פריטים באותה טבלה** — ✅ כך נבנה (גל J).
2. **מחיקת תווית סטטוס בלי יתומים** — ✅ גל R.
3. **יומן פעילות מהיום הראשון** — ✅ קיים; משמש ל-undo, לשחזור ערך ולביקורת.
4. **אוטומציות כמנוע אירועים** — ✅ קיים (`onItemEvent`), בנוסף למשימות מתוזמנות.
